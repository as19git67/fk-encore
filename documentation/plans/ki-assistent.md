# Assistant: one chat over everything the server knows

Status: stages 1 to 7 implemented (`POST /chat` in llm-service with its
benchmark in `llm-service/bench/`; the `assistant` service with the read
tools and the direct-debits endpoint; the chat page in the web app; write
actions as proposals the user confirms; follow-up questions on earlier
results and generated conversation titles; word positions, redacted
document bundles and grouped transaction reports; letters from selected
context). The benchmark ran on the production GPU on 2026-10-16; the
results are in the stage 1 section.
Tracking issue #1524, stages #1525–#1534; stage 8 (iOS) has its own plan
later.

## Problem

The server holds finance bookings, documents, photos, meter readings and
trip plans, each behind its own list page with its own filters. Four
questions show what is missing:

- "Welche Lastschriften muss ich in diesem Monat noch erwarten?" — the
  answer exists in `finance_recurring_mandate` (`last_seen +
  typical_interval_days`), but no page and no endpoint lists it.
- "Gib mir alle Protokolle der Eigentümerversammlung der Immobilie in
  München." — a hybrid document search with a category filter would find
  them, if the user knew to combine `q=Eigentümerversammlung München` with
  the right `kapitalanlage-immobilie-*` category.
- "Welche Urlaubsreisen haben wir letztes Jahr gemacht?" — recaps of kind
  `trip`, albums with an `event_name`, trip-planner plans and the photo
  timeline each hold a piece of it.
- "Mach mir ein Album mit allen favorisierten Bildern von 2025." — three
  calls (`GET /photos?favorite=true&dateFrom&dateTo`, `POST /albums`,
  `POST /albums/photos/batch`) that today need three screens.

Every answer is a composition of calls the server already has. What is
missing is the piece that turns a sentence into those calls, runs them as
the asking user, and writes the result back as a sentence with the rows
behind it.

## What exists

- `llm-service` runs `gemma-4-26B-A4B-it-qat-UD-Q4_K_XL` in production:
  a Gemma 4 Mixture-of-Experts model, 26B parameters with about 4B active
  per token, on a 16 GB GPU behind `llama-server` started with `--jinja`
  (`llama_supervisor.py:65`). That gives an OpenAI-compatible
  `/v1/chat/completions` with native `tools`, `tool_choice` and
  `stream`. The FastAPI layer exposes only `/classify`, `/embed`,
  `/json-prompt` and the vision endpoints — no chat, no tools, no
  streaming. The in-process backend (`llama-cpp-python`, the CPU image
  with Qwen2.5-7B) has no tool protocol; the trip-planner benchmark
  emulated tools by asking for JSON (`trip-planner/llm-bench/run-chat.ts`),
  and this Gemma model scored 10/10 against Claude's 9/10 there and 96 %
  on request understanding at a 1 s median (`documentation/ios-urlaubsplanung.md`
  §11).
- The 16 GB carry the Q4 weights, the KV cache, the vision projector and
  the E5 embedder together. The usable context window is whatever is
  left after those, and the active `LLM_CTX` is the budget the agent loop
  has to live in; `llm-service/README.md` has the arithmetic.
- Natural language already drove one domain: `POST
  /finance/analysis/query` (`finance/analysis.ts`, removed since) parsed a
  question into an AST via `/json-prompt`, then ran SQL. `POST /photos/search/natural`
  parses German photo queries into CLIP text, place and date.
- Permission is enforced in the services, not at the edge:
  `requirePermission`, `readableAccountIds()`, `visibleDocumentsWhere()`,
  `accessiblePhotoCondition()`, meter owner/group checks. A
  service-to-service call through `~encore/clients` carries the caller's
  auth data, so anything the assistant reaches through those clients is
  already scoped to the user.
- `ai-queue` hands out slots for the `llm` model; `checkRateLimit` guards
  the finance analysis at 30 questions per 10 minutes.
- Streaming to the browser exists once: `realtime/subscribe.ts`
  (`api.streamOut`) and `composables/useRealtime.ts`. Encore's
  `stream.send()` is synchronous on the server (see the comment there).
- Every list page keeps its filters in `route.query` (#1278). A URL is a
  complete description of a list, so the assistant can answer with a
  link that opens the real page with the right filters instead of
  re-rendering the list itself.
- Everything AI stays in-house (`documentation/ios-urlaubsplanung.md` §11.5). The
  Anthropic client exists only for benchmarks.

## Decisions

- **The assistant calls the app, never the database.** Tools are thin
  wrappers over existing service functions through `~encore/clients`.
  The user's auth data travels with each call, so the assistant can see
  exactly what the user can see, and nothing the model invents (an
  account id, a group id) opens a door the services would not open for
  that user. No SQL is generated by the model.
- **Read freely, write only after confirmation.** A read tool runs at
  once. A write tool (create album, add photos, set a tag, create a
  follow-up) returns a *proposal*: the server stores it with the exact
  arguments, the client shows a card with "Ausführen", and only a separate
  confirm call executes it. The model never executes a write by itself,
  and a proposal it did not create cannot be confirmed.
- **Local model, open protocol.** Chat goes through the OpenAI-compatible
  `/v1/chat/completions` of llama-server, proxied by llm-service. The
  model stays whatever the admin activates under "KI-Modell". A cloud
  model would fit behind the same protocol; it is deliberately out of
  scope, as in the trip planner.
- **The model always knows the whole menu, and reads the recipe on
  demand.** A question like "which trips last year and what did they
  cost" spans photos, trip plans and finance; a router that picks one
  domain up front cannot answer it. So every request carries the complete
  catalog: one line per tool, name and a sentence, across all modules the
  user may use (about 1 500 tokens for fifty tools). Full JSON schemas
  (150 to 400 tokens each) are not sent; the model fetches the ones it
  needs with a meta-tool `describe_tools(names)`, exactly as a deferred
  tool list works in an agent harness. The model decides what to combine,
  the server decides nothing in advance. Tool results are compact tables,
  capped in rows, with ids and totals, never full records, because fifty
  known tools do not help when one result of 500 bookings fills the
  window. The glossary (account labels, user tags, categories, person
  names) comes with the domain's first tool result, not up front.
- **The catalog is generated, the allow-list is written.** Encore knows
  every endpoint and emits the full specification with `encore gen client
  --lang=openapi` (`openapi/spec.json` in the repo is a hand-kept subset
  of 85 operations for iOS). The catalog is built from the generated
  specification at startup, so a new endpoint is known to the assistant
  without hand work. Two things stay manual, in
  `assistant/tool-allowlist.ts`: which operations are offered at all
  (deleting, sharing, FinTS sync and admin endpoints never), each one's
  `read` or `write` kind, and for the important ones a sentence written
  for the model ("overdue direct debits and amount changes of standing
  mandates" rather than "GET /finance/anomalies").
- **Generated text is a draft until the user says otherwise.** Where the
  model writes prose for the user (stage 7), the text is shown
  editable before anything is rendered or saved, the facts in it come
  from the context the server handed over, and the sender, date and
  layout come from the server. A letter is the user's letter; the model
  wrote the first version.
- **The model never does arithmetic.** Sums, subtotals, yields and date
  ranges are computed by tools and printed with their formula. The model
  chooses what goes into which group and names the groups; the server
  adds up. A number in an answer that no tool produced is a bug.
- **Work products are app objects, not loose files.** A bundle of
  documents is a Sammelmappe (`document_collections`, kind `manual`) with
  the existing redaction rectangles and the existing PDF export; a
  transaction report is a saved analysis with the existing PDF report.
  The user finds both again in the module, can edit the redactions by
  hand and rebuild the PDF, and the assistant does not need its own file
  storage.
- **The answer is text plus cards plus a link.** The model writes the
  sentence; the server attaches the rows it saw as typed result blocks
  (`transactions`, `documents`, `photos`, `albums`, `meters`, `proposal`)
  and, where a list page can show the same set, a `route` with the
  filters. The client renders the blocks with the existing row components
  and the route as "In der Liste öffnen".
- **Time is grounded by the server.** Today's date, the current month,
  "letztes Jahr" resolved to an ISO range, and the user's locale go into
  the system prompt. The finance analysis already does this with
  `resolveRelativeTimespan`; the assistant reuses it.
- **German in, German out; English in the repo.** The user speaks German;
  prompts and tool descriptions are written in English (the models follow
  them better), and the system prompt says to answer in the user's
  language.

## Stages

1. **Chat with tools on llm-service** (`llm-service/main.py`,
   `llama_server.py`).
   - `POST /chat`: `{messages, tools?, tool_choice?, max_tokens,
     temperature, stream}`, OpenAI message shape (`system`, `user`,
     `assistant` with `tool_calls`, `tool`). On the `server` backend it
     forwards to `/v1/chat/completions`; `stream=true` relays the SSE
     chunks. On the `inproc` backend it emulates tools with a JSON-grammar
     step (`{"tool": name, "arguments": {...}}` or `{"answer": text}`), the
     way the trip-planner benchmark did, without streaming.
   - Reasoning stays off (`LLM_REASONING=off`) for tool turns; a thinking
     block spends the context the tool results need.
   - The call goes through the single-worker executor like the others, so
     a chat turn and a classification never run at once on the CPU.
   - First check that llama.cpp's jinja template for Gemma 4 emits
     parseable `tool_calls` (the pinned `LLAMA_CPP_REF` decides this), and
     that a tool turn with the projector loaded fits the active `LLM_CTX`.
   - Benchmark (`llm-service/tests/`, and a small case file in the
     assistant service): the four questions above plus ten variants, run
     against the production Gemma model, scored on "right tool, right
     arguments" and timed per round. The CPU fallback is measured once
     for the record; the assistant is designed for the GPU deployment.

   - **Implemented** (#1525): `llm-service/chat.py` holds the request
     shape, the reply checks (a call must name an offered tool, its
     arguments must parse into an object, else `502`) and the inproc
     emulation; `main.py` adds the endpoint and the SSE relay. A prompt
     that does not fit `LLM_CTX` is a `413`, so the agent loop knows to
     shrink the history rather than retry. On `inproc`, `stream=true`
     keeps the wire format and delivers the finished reply as one chunk.
     Thinking is off per request (`chat_template_kwargs.enable_thinking`).
   - **Benchmark** (`llm-service/bench/chat_bench.py`, 16 cases in
     `chat_cases.json`): the questions above plus variants, as a small
     agent loop with canned tool results; a case passes when every
     expected call occurred with the right arguments and the run ended in
     an answer. Order of calls is free, extra read calls are not penalised.
     This script checks the raw tool protocol of `/chat` with its own
     simplified tool list and runs from any host. The benchmark that
     measures the assistant as it is deployed is the one in the app:
   - **Benchmark in the app** (Dokumente › Einstellungen › KI-Benchmark,
     `assistant/benchmark.ts`, cases in `assistant/bench/cases.ts`): every
     case goes through the real agent loop (`runTurn`) with the real system
     prompt, the real catalog (deferred schemas and `describe_tools`
     included), the context budget and the round cap of production; only the
     tools return canned, synthetic results, so nothing is read or written.
     The cases cover the questions above plus follow-ups on earlier
     results, redacted bundles, grouped reports and letters from a working
     set (25 cases). A test checks that every expected tool and argument
     exists in the catalog, so a renamed parameter fails CI rather than the
     benchmark. Each round runs in the ai-queue's `llm` slot at priority 5
     and is timed inside it. Runs are kept in `assistant_benchmark_run` with
     the model llm-service had loaded, so switching the model under
     KI-Modell and running again compares the two; a run can be cancelled
     and keeps the cases it finished.
     Results on the GPU host (16 GB VRAM), measured in the app on
     2026-10-16. The first row is the run before the fixes listed below it;
     the four rows after it are the same 26 cases on four models, after
     those fixes.

     | Deployment | Passed | Tool hit | Args hit | Median ms/round | p90 | Median rounds |

     What the four runs say:
     - **Gemma stays the production model.** Qwen3.6-35B-A3B passes one case
       more but needs five times the time per round (its first round after a
       tool result takes 10–12 s, single rounds up to 60 s), which on a chat
       is the difference between an answer and a wait. Qwen3-14B is as fast
       as Gemma and clearly weaker on the catalog: it reaches for
       `list_trip_plans` where `list_recaps` is asked, passes `year: 2026`
       for "gerade in Planung", narrows the previous photos without the
       `place` filter, and gives up on the Mahnung after
       `get_document_summary` instead of reading the text. Qwen2.5-7B on the
       CPU is not usable as an assistant: it answers Lastschriften, Reisen
       and Konten from imagination without a tool call, and asks the user
       for a meter id instead of calling `list_meters`.
     - **Both strong models miss the same two cases.** The Mahnung reply
       names the invoice number but not the deadline in the letter text,
       although the question asks for both; and the letter about three paid
       invoices either claims payment without a date gap (Qwen3.6, which
       puts its gaps into the recipient's address instead) or leaves a
       single-bracket "[Name des Nutzers]" the server cannot recognise
       (Qwen3-14B). The `body` parameter of `render_letter` now says that
       every fact the user asked to be named stands in the body.
     - **Gemma once answered with nothing**: `debits-this-month` ended after
       the tool result with an empty reply and scored as unanswered. The loop
       now asks once more, without tools, for the answer in words before
       giving up (the same request the forced last round uses).
     - **Gemma took a shortcut the tool silently ignored**: for "nur die aus
       München" it called `create_album(from_previous_result, photos:
       {place})` in one go; `from_previous_result` would have won and the
       album would have held all three photos. The tool now refuses the
       combination and names the way round (`list_photos` with the filter
       first), so the model can correct itself in the next round.
     - **One case punished looking first**: `report-by-tags` had no canned
       `list_transactions`, so a model that checked the bookings before
       building the report got "no data" and stopped (both Qwen3 models).
       The case now has rows for that call; only the report is scored.
     - Gemma searched the Eigentümerversammlung protocols with the town in
       `q` instead of the category, which the case counts as a miss while
       the rows would have been the same; left as is.

     What the first run showed, and what changed after it:
     - The three follow-up cases failed the same way: the model answered
       without a tool call and wrote "[tools behind this answer: …]" itself,
       copying the note the server appended to earlier answers (other answers
       gained "*Tools: …*" lines the same way). Earlier turns are now
       replayed as real tool calls with the digest as the tool result, the
       rule about notes says never to write them, such lines are stripped
       from answers, and an answer that writes a call as text is sent back
       once (`FAKE_CALL_NUDGE`).
     - "Zwei Module verbinden" ran all eight rounds, calling
       `list_transactions` with the same arguments three times, and ended
       in Gemma's raw call syntax as the "answer" (scored as answered). A
       repeated call is now answered with "already called, see above"
       instead of running again, and a forced last round that writes a call
       gets one more request without tools for the answer in words; failing
       that, the turn ends with `OUT_OF_ROUNDS`, which scores as unanswered.
     - The Mahnung reply named the deadline in the chat but not in the
       letter; the rules now say everything asked for goes into the letter
       text, dates as DD.MM.YYYY, and the server signs with the user's name
       in place of a "[[Dein Name]]" gap.
     - `list_trip_plans` was called with `year: 2026` for "gerade in
       Planung", which would miss a trip in 2027; its description now says
       to leave the year out, and the case checks that.

2. **The `assistant` service** (new, `assistant/`).
   - Tables `assistant_conversation` (`id`, `user_id`, `title`,
     `created_at`, `updated_at`) and `assistant_message` (`id`,
     `conversation_id`, `role`, `content`, `tool_calls` jsonb, `blocks`
     jsonb, `created_at`). Conversations belong to one user; nothing is
     shared.
   - `POST /assistant/conversations`, `GET /assistant/conversations`,
     `GET /assistant/conversations/:id`, `DELETE
     /assistant/conversations/:id`.
   - `api.streamOut` `GET /assistant/conversations/:id/ask?message=` —
     the handshake carries the question, the stream sends `token`,
     `tool_start`, `tool_result` (the typed block), `route`, `done` and
     `error` events, then closes. Reconnection is not needed: a turn is
     short, and a lost turn is asked again.
   - Agent loop (`assistant/agent.ts`): system prompt with time
     grounding, the full one-line catalog of the tools this user may use,
     and two or three worked examples of chained calls → up to eight tool
     rounds → final answer. Each round is one `/chat` call; the loop stops
     on an answer without tool calls, on the round cap, or on the context
     budget (older tool results are replaced by their digest first,
     history second).
   - Catalog (`assistant/catalog.ts`): built at startup from the generated
     OpenAPI specification plus `tool-allowlist.ts`. Each entry has a
     name, the one-line description, the JSON schema derived from the
     operation's parameters, a `permission` (the module permission plus
     the domain's view permission), a `kind` (`read` | `write`) and a
     runner. `describe_tools(names)` returns the schemas of up to five
     entries. A user without the permission does not see the entry at
     all, so the model cannot even ask for it.
   - Hand-written tools (`assistant/tools/*.ts`) exist only where an
     endpoint is not the right shape for the model: a composite that
     saves rounds (`upcoming_payments`, formerly `upcoming_direct_debits`), a result that needs
     trimming or a route (`search_documents` returning rows plus the list
     URL), or a computation (stage 6). They register in the same catalog.
   - Read tools of this stage:
     - finance: `list_transactions` (the `/finance/transactions` filters;
       a list for one account carries the account and its balance as the
       block's subtitle, as the list page has), `transaction_totals`
       (sums with subtotals by tag or period; it replaced `analyze_spending`
       when the analysis page was removed), `list_accounts` (the accounts as arranged on
       the Übersicht page, `GET /finance/overview`, with section and
       latest statement balance — "meine Konten" are the ones the user
       placed there, not the account table; a cash account has no balance
       and the row says so), `upcoming_payments` (new, see below).
     - depots (`assistant/tools/depot.ts`): `portfolio_overview`
       (`GET /finance/portfolio` — market value, cost basis, unrealized
       and realized gain, income, fees, taxes, total return, positions
       with value and gain, per-year figures; `q` finds a security's key),
       Each position names the depot(s) holding it, so "in welchem Depot
       liegt X" and "was liegt im Depot Y" (`account_ids`) are one call.
       `position_detail` (`GET /finance/portfolio/positions/:key` — one
       security with share per depot, sales with gain, years,
       transactions), `depot_transactions`
       (`GET /finance/portfolio/transactions` — buys, sells, dividends by
       security, kind and period, with the server's sums), `quotes`
       (`GET /finance/quotes` — last price, change over a range, unread
       news, and the totals the Kurse page shows: value of the holdings
       and their change over the range, so "habe ich heute Gewinn gemacht"
       is `range=1d`) and `position_news` (`GET /finance/quotes/news`). All
       arithmetic is the finance service's; the blocks `positions`,
       `depot_transactions`, `quotes` and `news` link to the Portfolio,
       position and Kurse pages.
     - tax: `tax_documents` (`GET /documents/tax` — the documents
       flagged for one tax year, grouped by Anlage as the Steuer page lists
       them), `search_documents(tax_relevant)` and
       `list_transactions(tax_relevant)` read the flags documents and
       bookings carry; the write tool `tax_return_bundle(year)` proposes a
       mixed Sammelmappe (`POST /collections`) of every flagged document of
       the year plus the bookings marked tax-relevant in it, which the user
       then exports, sends or shares from the folder's page. Filling in the
       forms: `tax_worksheet(year)` (`assistant/tax-worksheet.ts`) arranges
       what the household holds the way the forms ask for it — per Anlage
       the flagged documents with the amount recognised in each
       (`GET /documents/:id/receipt-suggestion`, first 80 documents) and
       the sum, the bookings marked tax-relevant in the year summed by tag,
       the depot's income, gains and taxes of the year from the portfolio,
       and hints (an Anlage that had documents last year but none yet,
       documents without a recognised amount); `tax_worksheet_pdf(year)`
       stores it as the document "Ausfüllhilfe Steuer <Jahr>"
       (`assistant/tax-worksheet-pdf.ts`, pdfkit) linked to the flagged
       documents. Recognised amounts are marked unchecked everywhere; the
       user confirms each against the document. The same worksheet opens
       without a chat from the Steuer page ("Ausfüllhilfe" for the chosen
       year and Steuerakte): `GET /assistant/tax-worksheet` and `POST
       /assistant/tax-worksheet/pdf` in `assistant/tax-worksheet-api.ts`,
       dialog `components/documents/TaxWorksheetDialog.vue`. The Anlagen list
       (`documents/tax-sections.ts`) gained KAP-INV and AUS. A prompt rule
       routes "Steuer <Jahr>" questions there and forbids the model to
       judge tax relevance or compute a tax figure itself.
     - documents: `search_documents` (hybrid search with filters; `sort`
       switches the relevance ranking to document date, because the rows
       next to the answer follow the tool's order, not the model's text;
       `mode` picks `fts` for a rare term that the hybrid ranking would
       surround with near misses; `correspondent` takes the sender as the
       user names it and resolves it against `GET /documents/correspondents`
       to the slug, else filters the sender line), `list_categories`,
       `get_document_summary` (one or several ids in one call — the rule in
       the prompt says a "ja" to the assistant's own offer acts on the rows
       of the previous answer, never on a new search). `search_documents` and `search_photos` are
       marked `refines`: a second call in the same turn replaces the first
       call's block beside the answer, since a model that searches again did
       not like what it found; lists (two accounts, two meters) keep both.
       Beyond that, a document or photo block replaces every earlier block
       of its kind in the turn whatever tool made it (`narrowingFamily` in
       `agent.ts`): the tax listing, then a search, then the summary of the
       three it read are one trail to one list, and the steps line keeps
       the trail. The chat still folds older lists of a kind in one stored
       answer, for answers from before this rule. When the rows do not
       answer the question at all (asked for flights, found coffee bills),
       the model ends its answer with the line `[[ohne Liste]]`
       (`NO_ROWS_MARKER`); the agent strips it and drops every block but a
       proposal card, so the answer stands alone.
     - photos: `photo_comments` (`GET /photos/:id/comments`, the comments
       under one photo in an album) and `photo_activity` (`GET /feed`,
       filtered by kind, album, photo or unread — the discussions around
       the photos), `list_album_shares` (who the user's shared albums are
       shared with — the "participants" of an album are its shares, not
       the persons on its photos; one `GET /albums/:id/shares` per owned
       album, at most 40 per call, albums shared *with* the user listed
       with their owner only), `list_albums` (with `shared` and the
       owner), `list_photos` (favorite, dates, persons, place — the place
       is matched on the server as `locationText` of `GET /photos`, since
       filtering the newest 2000 here missed every older photo from it;
       `order=oldest` for "das älteste Foto", `limit` for how many rows are
       shown),
       `search_photos` (natural search), `list_recaps` (kind `trip`),
       `list_albums`.
     - meters: `list_meters`, `latest_readings`, `consumption_report`.
     - trip planner: `list_trip_plans`.
   - New endpoint behind `upcoming_payments`: `GET
     /finance/mandates/upcoming?until=` lists active recurring mandates
     whose `last_seen + typical_interval_days` falls in the window, with
     the typical amount, scoped by `readableAccountIds()`. This is also a
     useful page on its own (Finanzen › Lastschriften), independent of the
     assistant.
     **Implemented** (#1526): `finance/upcoming-debits.ts` with
     `GET /finance/mandates/upcoming?from=&until=` (default: today to the
     end of the month) and the page Finanzen › Lastschriften. Outgoing,
     non-card series with at least three bookings and an interval of 7 to
     400 days; a series that missed two cycles has ended. Whether a series
     is regular is read from its last twelve bookings, not from the
     mandate's running average: the intervals and the amounts must vary
     little (`seriesProfile`, `isRegular`), so a shop visited every few
     weeks for a different basket each time is not "expected". The cadence
     is the median gap, the amount the median of the newest bookings. A
     series that went on under another mandate — the insurer moved to a
     new account — is superseded by that one and listed once
     (`isSuperseded`, with the detector's `isLikelySeriesContinuation`).
     Intervals near a month, quarter, half year or year step by calendar
     months from `last_seen`, so a series on the 1st stays on the 1st. A
     booking up to seven days late is still listed, marked overdue. The
     response carries the sum, so neither the page nor the model adds up.
   - Guards: `checkRateLimit` per user (20 questions per 10 minutes), the
     `llm` slot from `ai-queue`, a per-conversation context cap, and
     `APIError.unavailable` with the same "try later" semantics as the
     other llm clients when the model is reloading.
   - Logging: each tool call with its arguments and row count, no row
     content, so a wrong answer can be traced to the call that produced
     it.

   - **Grounding check** (after a first test answered "die 10 neuesten
     Buchungen" with invented rows): the system prompt now opens with "You
     know nothing about this user's data" and an example for that question.
     Besides, `runTurn` sends an answer back once when the model called no
     tool in the turn but the answer reads like the user's data (an amount,
     a date, or three list lines with numbers, `looksLikeUserData`). The
     draft is withdrawn on the stream (event `retract`) and never stored;
     the model gets `GROUNDING_NUDGE` and either calls the tool or, when the
     figures come from an earlier result, repeats itself, which is then
     accepted. The benchmark has the case `latest-bookings`.
   - **Implemented** (#1527), with three deviations from the text above:
     - *Asking is a POST, the stream only watches.* A browser can open a
       WebSocket only with `?token=`, and the gateway downgrades that token
       to the media scope (`user/auth-handler.ts`), under which every
       `requirePermission("finance.view")` fails — in the assistant and in
       every service its tools call. So the client picks a turn id, opens
       `GET /assistant/turns/:turnId/stream` (`api.streamOut`, events
       `token`, `tool_start`, `tool_result`, `done`, `error`), then posts
       `POST /assistant/conversations/:id/ask {message, turnId}` with the
       full bearer token. The agent runs in the POST, which also returns the
       whole answer; `assistant/live.ts` hands the events to the stream
       in-process and replays what a late stream missed.
     - *The generated part of the catalog is small for now.*
       `openapi/spec.json` is the iOS subset (photos, albums, persons,
       auth). `catalog.ts` builds tools from it through
       `tool-allowlist.ts` (`list_persons` so far) and warns about
       allow-listed operations the spec lacks; the stage's read tools are
       hand-written in `assistant/tools/` because each needs trimming or a
       list route. Regenerating the spec with every service
       (`scripts/generate-openapi.sh`) lets the allow-list grow; each entry
       still carries one line that calls its endpoint
       (`invoke: () => photo.listPersons()`), because Encore's parser accepts
       a service client only as a direct call, never looked up by name.
     - *Trip plans are read through the plan store*, with the endpoint's own
       `photos.view` check: the client name Encore generates for the
       hyphenated `trip-planner` service could not be checked without the
       Encore CLI.
     Schemas: up to `ASSISTANT_SCHEMA_BUDGET_TOKENS` (9000) every tool's
     schema goes along; past it the model gets the one-line catalog and
     `describe_tools`. The context budget follows the model's window
     (`n_ctx`, which llm-service names in a closing `context` chunk of every
     `/chat` stream) less 5 % and the answer, converted to the loop's
     characters / 4 estimate with a ratio learnt from the real token counts;
     `ASSISTANT_CONTEXT_TOKENS` pins a fixed budget instead, and 20000 holds
     until the first reply has named the window. Older tool results shrink to
     digests first, the oldest first, then the oldest history turns go, and a `413` from llm-service shrinks
     everything once more and retries the round. The last round sends
     `tool_choice: "none"`, so the loop always ends with an answer. Each
     `/chat` call takes the `llm` slot of the ai-queue at priority 0, a
     level reserved for the assistant (`AI_PRIORITY` in
     `ai-queue/slot-helper.ts`): it is next whenever the slot frees, ahead of
     a queued classification batch and of receipts. The whole turn runs in
     that lane (`withAiPriority`), so a tool that asks the model is queued at
     0 too. Every other llm-service client (finance, trip planner, collection
     summaries, recap titles, document classification outside a worker) takes
     the slot as well, so the service's single inference slot is never held
     by a caller that skipped the line. A running job is not interrupted. Tool
     calls are logged with their arguments and row count, never row content.

6. **Work products: bundles, redactions, reports.** The example that
   needs all of this:

   > "Zeige mir alles, was beim Kauf der Immobilie in München relevant
   > war." → documents and bookings. Then: "Schwärze den Kaufpreis in den
   > Dokumenten und erzeuge ein PDF mit all diesen Dokumenten. Mach ein
   > zweites PDF, in dem alle Finanztransaktionen gelistet werden, inkl.
   > Summe, mit Zwischensummen für Kauf, Sonderzahlungen wegen Reparatur,
   > Mieteinnahmen, und ermittle die bisherige Rendite."

   - **Prerequisite: the text keeps its positions.** A document that has
     been through OCR already knows where every word stands; today
     `text_extract` parses Tesseract's TSV into `OcrWord[]` (pixel boxes
     with confidence, `documents/ocr-layout.ts`), lets the resolver
     correct the rows, renders the layout text — and drops the boxes.
     Born-digital PDFs go the same way: `pdf-text-layout.ts` reads each
     item's transform for the spacing and keeps none of it. Nothing is
     re-run later: `text_extract` writes the corrected rows per page into
     `document_page_words` (`document_id`, `page`, `width`, `height`,
     `words` jsonb of `{text, left, top, right, bottom, confidence?}`,
     pixels for a scan, points for a born-digital page), at the same
     moment it writes `extracted_text`. The box of a word, divided by the
     page size, is the 0..1 rectangle the redactions already use. Existing
     documents get their rows by the targeted re-extraction that exists
     for OCR changes (`text-extract.ts` prioritises by quality), run once
     as a backfill. Stage 6 does not start before this is in place.
     **Implemented** (#1531), with these details: the table also keeps the
     page's `unit` (`px`/`pt`) and `rotation` (what OCR turned the raster
     by, or the page's /Rotate), since a box is only meaningful against
     the image it was measured on. Words are stored flat in reading order;
     `findTextBoxes` (`documents/page-words-store.ts`, matching in
     `page-words.ts`) joins adjacent words on one line and puts a currency
     sign or code next to an amount into the same box. There was no
     targeted re-extraction to reuse, so the backfill is its own queue
     service `page_words` (`POST /documents/page-words/backfill`, button
     "Wortpositionen nachtragen" in the document queue panel): lowest OCR
     confidence first, then oldest; the worker runs only while no
     text_extract is queued, leaves status and classification alone, and
     replaces the text only when a re-OCR reads it differently (then the
     embedding is redone). On the way it turned out that the text layer
     had not been read at all since `pdf-parse` 2 dropped its v1 function
     (every born-digital PDF went to OCR); it is now read with `pdfjs-dist`
     directly (#1572).
   - `find_text_in_document(document_id, query)` reads
     `document_page_words` and returns the pages and rectangles where a
     value stands (`{page, x, y, w, h}` in the 0..1 page coordinates
     `document_collection_members.redactions` already uses), merging
     adjacent words into one box. An amount is matched in all its printed
     forms ("450.000,00 EUR", "450.000 €", "EUR 450.000,-"), so one
     `query` covers the purchase price wherever it appears. A document
     without stored rows is reported as such, not re-OCR'd on the spot:
     the answer names it so the user can trigger its extraction.
   - `create_collection(name, document_ids, redactions)` creates a manual
     Sammelmappe through `/document-collections` with the rectangles per
     member, and `build_collection_pdf(collection_id)` triggers the
     existing export (`documents/collection-pdf.ts`: rasterized, burnt-in
     redactions, fresh text layer). Both are write tools, so the turn
     ends in a proposal card that says "Sammelmappe ‚Kauf München' mit
     14 Dokumenten, Kaufpreis auf 6 Seiten geschwärzt"; after "Ausführen"
     the answer carries the download link and the link to the
     Sammelmappe, where the user checks and corrects the boxes by hand
     before passing the PDF on. A missed box is not a risk the assistant
     should take alone.
   - **Implemented** (#1532), with these details: the boxes come from
     `GET /documents/:id/text-boxes` (the document's own visibility check),
     and `create_collection` takes the values to black out (`redact`), not
     rectangles — the server finds the boxes when the proposal is made, so
     the card's page count is the truth and the model never copies
     coordinates. Boxes are padded by 15 % of the line height on every
     side; on a born-digital page a word's place inside its text run is
     estimated from Helvetica advance widths, since pdf.js reports one width
     per run. `create_collection` also starts the PDF (`build_pdf`, default
     on); `build_collection_pdf` does it for an existing folder. The result
     links the folder page (`/dokumente/mappen/:id`), where the PDF is
     downloaded once built. Documents without stored positions are named on
     the card and left unredacted.
   - `transaction_report(title, groups, yield?)` takes the grouping the
     model made — `groups: [{name, transaction_ids}]`, one booking in at
     most one group, the rest in "Sonstige" — and computes per group the
     subtotal and count, the grand total, and, when `yield` is given,
     the return with its formula printed: `yield: {investment_group,
     income_groups, cost_groups}` → net income over the period divided by
     the investment, as a total and annualised over the span from the
     first investment booking to today. The server does all sums; the
     PDF comes from `finance/pdf-report.ts` extended by group headings
     and a formula footer. The report is stored as a saved analysis
     (`/finance/saved-analysis`) so it can be re-run with new bookings,
     and the proposal card shows the groups with their counts before
     anything is built.
   - **Implemented** (#1533), with these details: not stored as a saved
     analysis — that table holds a tag filter (`AnalysisAst`) the analysis
     page renders, and a list of groups by booking id does not fit it. The
     report has its own table `finance_grouped_report` (migration 0250)
     that keeps the definition only; every run computes the numbers from
     the bookings as they are (`finance/grouped-report.ts`, in cents). A
     group is either booking ids or one user tag — a rule, so a re-run
     picks up bookings tagged since. Endpoints under
     `/finance/reports/grouped` (preview, save, list, re-run, delete, PDF).
     The yield is simple, not compounded: net income (income + cost groups)
     over the investment, per year divided by the years since the first
     investment booking; formula and period are printed and handed to the
     model as the only figures it may repeat. The proposal card's result
     carries a download (`result_download`), so the PDF is fetched with the
     user's token from the card.
   - Grouping is where the model earns its keep: it sorts bookings by
     counterparty, purpose and the user's tags ("Miete", "Reparatur") and
     explains a doubtful one in the answer rather than hiding it. A
     booking the model cannot place stays in "Sonstige" and is listed,
     never dropped.
   - Both PDFs render in the background like the collection export
     today; the stream reports `tool_start` and the answer links the
     result when it is ready, or says where to find it (the Sammelmappe,
     the saved analysis).

7. **Text generation: a letter from what the app knows.** The example:

   > A letter is needed quickly — to print, or to send by mail — and
   > selected documents, photos or bookings are its context. The result
   > is downloaded or shared, or saved as a new document in the system,
   > possibly together with its context in a Sammelmappe.

   This is the one stage where the model's own words are the product.
   Everything around the words stays with the server.

   - **Context comes from a selection.** Three ways in: the working set
     of the conversation (stage 5: "schreib dem Verwalter wegen dieser
     drei Rechnungen"); a list selection or the basket handed over with
     a new `SelectionBar` action "An den Assistenten" (opens the chat
     with the selected ids as context, which is what the basket is
     for); and a document's detail page with "Antwort entwerfen"
     (context = this document, recipient = its correspondent). The
     context is a list of typed references; the server renders each into
     a compact brief for the prompt — a document as title, date, sender,
     reference numbers and summary, a booking as date, counterparty,
     amount and purpose, a photo as date, place and description — never
     the full text, unless the model asks for one document with
     `get_document_text`.
   - **The draft is text in the chat, editable.** The model writes the
     letter body in the answer (streamed, in the user's language, in the
     tone asked for). Facts in it — amounts, dates, reference numbers —
     are copied from the context briefs; the system prompt says to use
     only what the context carries and to leave a bracketed gap
     (`[Datum der Zahlung]`) for what it does not. The answer ends with
     the list of context objects used, so the user sees what the letter
     rests on.
   - `render_letter(body, recipient?, subject?, attachments?)` is the
     write tool. The server supplies what the model must not invent: the
     sender block from the user's profile, today's date, the recipient
     from a document's correspondent or the user's input, and the layout
     — a DIN 5008 letter with address window and fold marks, drawn with
     pdfkit next to `finance/pdf-report.ts`. The proposal card shows the
     draft in an editable field, recipient and subject as inputs, and the
     three destinations as checkboxes; "Ausführen" renders the text as
     edited, not as drafted.
   - **Three destinations, all through existing paths.** *Download* is
     the rendered PDF. *Save as document* posts the PDF to `POST
     /documents` like an upload, so it runs through extraction and
     classification and gets `source = assistant`, with a link to the
     conversation and to the context documents (the existing
     related-documents panel then shows the letter next to the invoices
     it answers). *Sammelmappe* creates a manual collection with the
     letter as its first member and the context documents behind it, so
     the existing export yields one PDF with the letter as cover and the
     enclosures in order — which is what "anbei die Rechnungen" needs.
   - **E-mail** in this stage is a `mailto:` link with subject and body
     and the PDF already downloaded for attaching, because the user's
     mail client holds their identity, signature and sent folder. Sending
     from the server through the SMTP that `user/mail.ts` already uses
     for invites is possible later, but a letter to an arbitrary
     recipient leaving the server unseen is a step that needs its own
     decision (confirmation, a copy saved as document, a sent log).
   - Photos as context: the brief carries date, place and description;
     a letter that should carry pictures ("hier die Fotos vom Schaden")
     gets them as attachments through the same Sammelmappe path, each
     photo as a page via `receipt-pdf.ts`'s single-image page.
   - Follow-ups edit the draft in place: "kürzer", "förmlicher", "nenne
     auch die zweite Rechnung" produce a new draft from the same context;
     the card keeps the latest.
   - **Implemented** (#1534), with these details:
     - The working set is a column `context` on `assistant_conversation`
       (migration 0251), set when the conversation is created or with
       `PUT /assistant/conversations/:id/context`. `assistant/briefs.ts`
       renders each object into a few lines for the system prompt and a
       label for the chips above the question field; an object the user
       cannot see is named as such, never described. Without an earlier
       result of a type, `from_previous_result` means the working set's
       objects of that type.
     - Entry points: "An den Assistenten" in the selection bars of
       documents, bookings and photos, and "Antwort entwerfen" on a
       document page, all opening `/assistent?context=…`
       (`utils/assistantContext.ts`). The basket has no entry of its own
       yet; its members can be selected in their lists.
     - The draft goes straight into the `render_letter` proposal rather
       than into the answer text first: the card is the editable field.
       Gaps are written `[[…]]` (double brackets, so a bracket in a
       quoted reference does not count) and the card refuses "Ausführen"
       while one is left; the server checks again.
     - The sender block is the user's name plus `users.postal_address`.
       The first letter asks for the address as a gap; the address typed
       on the card is kept for the next one.
     - `assistant_letter` keeps the fields, not the PDF;
       `GET /assistant/letters/:id/pdf` renders it on demand
       (`assistant/letter-pdf.ts`, form B).
     - *Save as document* goes through the internal endpoint
       `POST /documents/generated` rather than the raw upload, and links
       the letter to its enclosures in the new table `document_links`.
       The related-documents panel shows the link from both sides as its
       first group, "Antwort und Bezug". There is no `source = assistant`
       column; the link and the letter row say where it came from.
     - Photos are context only; enclosing them as pages is left for later.

## How the example questions run

| Question | Router | Tools | Answer |
|---|---|---|---|
| Lastschriften diesen Monat | finance | `upcoming_payments(channel=direct_debit, until=end of month)` | Table of series with date, channel and amount; route to the page Erwartete Zahlungen (renamed from Lastschriften once it listed transfers too; `channel` narrows to direct debits or transfers, card payments and cash accounts never count) |
| Protokolle Eigentümerversammlung München | documents | `list_categories` → `search_documents(q, category=kapitalanlage-immobilie-*)` | Document rows; route `/dokumente?q=…&category=…` |
| Urlaubsreisen letztes Jahr | photos (+ trip planner) | `list_recaps(kind=trip, year)`, `list_trip_plans(year)`, `list_albums(hasEvent, year)` | One line per trip with dates and place; photo cells |
| Album mit Favoriten 2025 | photos | `list_photos(favorite, 2025)` → proposal `create_album` + `add_photos_to_album(from_previous_result)` | Proposal card, album link after "Ausführen" |
| Alles zum Kauf der Immobilie München | documents + finance | `search_documents(q, category=kapitalanlage-immobilie-*)`, `list_transactions(q=…)` or `transaction_totals(tags)` | Document rows and booking rows, both kept as the working set |
| Kaufpreis schwärzen, zwei PDFs, Rendite | documents + finance (stage 6) | `find_text_in_document(each doc, purchase price)` → proposal `create_collection` + `build_collection_pdf`; grouping by the model → proposal `transaction_report(groups, yield)` | Two proposal cards; after "Ausführen" two PDF links, the Sammelmappe and the saved analysis |
| Anschreiben an den Verwalter zu drei Rechnungen | documents (stage 7) | context briefs of the three documents → draft in the answer → proposal `render_letter(body, recipient=correspondent, attachments)` | Editable draft card; after "Ausführen" the PDF, the new document, or the Sammelmappe with the letter as cover |

The two-turn example is the one that decides the architecture: the
second turn works only because the first turn's rows stay addressable
(stage 5), because the model knows the document and finance tools at
once (the catalog), and because sums and the yield come from a tool, not
from the model.

## Open questions

- How many tool rounds a question may take before the wait is too long:
  stage 1's timing answers it. If the CPU fallback cannot carry a tool
  turn, the assistant is offered only when the active config runs on the
  `server` backend, and the page says so.
- "Immobilie" has no entity. The second question works through
  categories and the search text today; a property entity (address,
  documents, meters, bookings) is its own feature and not a prerequisite.
  The purchase example makes the case for it stronger: "everything
  relevant to the purchase" is a search today and would be a lookup with
  an entity. It is also the natural home of the yield, which the saved
  analysis of stage 6 only approximates.
- Which rows `document_page_words` keeps: the resolver-corrected rows
  (what the letterhead read and the classifier see) rather than
  Tesseract's raw words. The corrected ones are what the stored text was
  rendered from, so a search over the text and a search over the boxes
  find the same thing. The uncorrected reading is not kept.
- What the yield means has to be printed, not assumed: gross rent over
  purchase price is one number, net of repairs and annualised another.
  The tool prints its formula and the period on the report, and the
  answer repeats it in one sentence.
- Whether the header chat icon should open a drawer over the current
  page (context: "diese Liste als Album") instead of a page. Stage 3
  starts with the page; the drawer can come once the page is right.
- Audit: the tool log (stage 2) is enough for debugging. Whether answers
  should be kept beyond the conversation (for "was habe ich letzte Woche
  gefragt") is a question for stage 5.

## Operations

- A new service, two to three new tables, one new finance endpoint, and
  for stage 6 one more table (`document_page_words`) that `text_extract`
  fills from then on plus a one-time backfill over the corpus — the same
  re-extraction an OCR change needs, so it costs one pass of OCR time,
  scheduled through the scan queue. No change to the model deployment;
  the `--jinja` flag is already set.
- The chat competes with classification and the OCR vision calls for the
  single inference worker and the one KV cache. A question asked while a
  classification batch runs waits only for the job that is running, not for
  the queued ones; the stream shows
  `tool_start` events so the wait is explained. Decode is quick with 4B
  active parameters; the rounds' prefill is what adds up.
- Conversations are personal data of the user; they are deleted with the
  user and excluded from backups' public exports like the documents.

## Permissions (#1648)

The assistant is a role of its own, "Assistent User" with `module.assistant`
only; the module roles no longer carry it. The seed grants it once, in the
start that creates the role, to everyone holding a module role, so nobody
lost the chat on the upgrade and an admin's later withdrawal stands.

The system prompt names the areas the user may use and those without
permission (`assistant/access.ts`, by the same permissions the read tools
ask for) and the write tools the catalog offers. A question about an area
without permission is answered with the missing permission, not with "keine
Daten"; the data-question nudge leaves such an answer alone. Only whole
areas are named: inside an area the services filter on their own, and the
assistant never says that something hidden exists. A tool refused with
`permission_denied` reaches the model as "no access". The section grants
nothing — the catalog, the tool run and the services still check every
call. Benchmark case `balance-without-finance`.
